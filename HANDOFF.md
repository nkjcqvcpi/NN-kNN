## 2026-11-22: run tracking (TensorBoard)

Owner's rules: per-run training data goes to TensorBoard event files under `NN-KNN/runs/<workstream>/<study>/<unit>/` through `model/common/tracking.py`, with the run's weights in the unit; summaries keep their files and formats; recording was opt-in that day and became mandatory the same evening (next section). In T3 only `tools/t3_need_matching.py` trains anything, so it is the one entry point that records:

- `--study S`: one unit per seed, `runs/t3/S/s<seed>/`. Unit config: tool, seed, epochs, dimensions, objective, selection, term frequency and the SHA-256 of the SQuAD train file, the sample file and the need-query file (no host paths). Recorded: `rec/protocol` (the protocol of the session that started the unit), per-epoch curves `fit/` and `tune/` `mean_need_loss`, `source_recall_at1`, `source_recall_at2` (step = epoch, 0 = before training) and `train/mean_loss`, `train/mean_gradient_norm` (epochs 1..E), every training step as the row record `training_events` (the content of the old `training_events.json`), the seed summary as finals (`seed`, `selected_epoch`, `selected/<group>/<metric>`, `bm25/<group>/<metric>`, `actual_training_steps`, `nonzero_gradient_steps`, `parameter_delta_l2`, `trainable_parameters`, `training_seconds`), and the named state `metric` (`weights/metric.pt`: the same dict as the old `metric.pt`, with selected, final and initial metric and Adam states).
- With `--study`, `s<seed>/metric.pt`, `s<seed>/training_events.json` and `s<seed>/summary.json` are no longer written. `protocol.json` (plus `"study": "S"`) and `summary.json` still go to `--output`, with the same content; `summary.json` is rebuilt from the units (`seed_result`), and `checkpoint_sha256` is then the SHA-256 of the unit's `weights/metric.pt`. Rerunning a study skips complete seeds (their recorded summary fills `summary.json`), raises `ConfigMismatchError` if a setting changed, and resumes an interrupted seed after its last checkpointed epoch.
- Without `--study` the tool wrote exactly the files it wrote before (removed by the next section).
- Readers: `model/t3/metric_provenance.py` (`metric_provenance`, `metric_checkpoint_sha256`, `load_metric_checkpoint`) accepts a legacy `s<seed>/metric.pt` (bound through the files next to it, as before) or a run unit (verified weight file, unit records). `tools/t3_public_host_pilot.py` and `tools/t3_internal_host_pilot.py` take either as `--metric-checkpoint`. A unit binds only to pilots run from that unit: its `checkpoint_sha256` is the SHA-256 of `weights/metric.pt`, whose bytes differ from a legacy `metric.pt` with equal tensors (the core serializes it on its own: other archive name, pickle and serialization id; the tensor data members are byte-equal). So an existing audited pilot run (`--source-run` of `t3_internal_host_pilot`) still needs the legacy `metric.pt` it was run with; a unit given there fails with `source retrieval checkpoint mismatch`. The unit reader also checks that the recorded protocol agrees with the unit config (epochs, data, selection, objective, term frequency, dimensions, need-query file).
- Not recorded: the host pilots (`t3_public_host_pilot`, `t3_internal_host_pilot`, `t3_public_set_utility`, `t3_prompt_pilot`), the host need collection `t3_train_need_queries`, and `t3_host_smoke`, `t3_public_data_audit`, `t3_prepare_host`. They train no parameter (`trainable_host_parameters=0`); their output folders are audited evaluation evidence that later tools read by byte hash (`--input-run`, `--source-run`, `--reference-run`), so they keep writing them. `t3_prompt_pilot`'s `retriever.pt` is an untrained, hand-biased fixture core (no backward pass), not training weights. `results/README.md` (ignored, only on g234) still describes file-only outputs; update it there when the owner allows.
- Checked on g234 CPU (scratch copies): with the same seeds the old and new tool write byte-identical `s<seed>/` files; a `--study` run records the same seed summaries (except wall time), training events and metric tensors; a rerun of a complete study writes byte-identical `summary.json` and `protocol.json`; the full default study (seeds 8/9/10, 20 epochs), crashed in seed 9 and resumed, reproduces the 2026-10-05 original run exactly. Tests: `tests/test_t3_need_matching_runs.py`.

## 2026-11-22 (final): mandatory recording, summaries from runs, never retrain

Owner's final rules O1-O5 (see `reports/2026-11-22-tensorboard-strict-spec.md` on the hub) applied to T3:

- `tools/t3_need_matching.py` requires `--study` (argparse error, exit 2, without it). The file-only mode and the code that wrote `s<seed>/metric.pt`, `s<seed>/training_events.json` and `s<seed>/summary.json` are removed. `protocol.json` (always with `"study"`) and `summary.json` are generated from the units and go to `--output`, by default `results/t3/s1_single_hop_retrieval/need_matching/<study>/`. A rerun may reuse that folder: it may hold only those two files of the same study; a folder with anything else (an old result folder) or another study's summary is refused and left untouched.
- Never retrain (O4): every seed is looked up with `tracking.load_unit` before any training; a complete seed is neither trained nor evaluated again, its recorded summary and weight hash fill `summary.json`. The tool draws only on a per-seed `random.Random(seed)` and resets the shared metric and a fresh Adam at the start of each seed, so no later seed depends on RNG or model state left by an earlier one and no RNG snapshot is needed. Resume files stay in the unit after it completes (O5).
- `model/t3/metric_provenance.py` reads only run units; a legacy `s<seed>/metric.pt` raises `ValueError` (`not a t3_need_matching run unit`). The two host pilots therefore take only a unit as `--metric-checkpoint`. An audited pilot run made from a legacy `metric.pt` (`--source-run` of `t3_internal_host_pilot`) cannot be continued with a unit (the weight hashes differ); this was already so.
- Host tools are not run units: they train nothing (`trainable_host_parameters=0`) and their output folders are byte-bound evaluation evidence for later tools and the external verification files, so they keep writing them. Their outputs belong under `results/t3/<stage>/`; none writes into `reports/` or `docs/`. `t3_prompt_pilot`'s `retriever.pt` is an untrained fixture core.
- `codex/smoke_test.py` is main's version (plus the T3 imports): `--mode train|classification` require `--study` and record to `runs/core/<study>/smoke/<mode>`; a complete smoke unit is reported, not retrained.
- Checked on g234 CPU (scratch copies, real SQuAD fit/tune data, seeds 8 and 9, 4 epochs): the new tool's summaries equal the pre-change tool's file-mode seed summaries and `--study` summaries (except wall time), its unit weights are tensor-equal to the old `metric.pt`, its training events equal the old `training_events.json`; a study crashed inside seed 9 (once without and once with a resume checkpoint) reruns without touching seed 8 and gives the numbers, weights, events and curves of the uninterrupted study. Tests: `tests/test_t3_need_matching_runs.py`, `tests/test_t3_metric_provenance.py`.
- Left alone: `results/README.md` on g234 (ignored) still describes the file-only outputs; old results there are not touched.
