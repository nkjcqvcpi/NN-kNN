# Shared NN-kNN core

This file is identical on every branch. It defines the NN-kNN core that the four workstreams share and the rules for changing it.

## Workstreams

| Folder | Branch | Contents |
| --- | --- | --- |
| `nnknn/` | `main` | Standalone NN-kNN model: the core below, its supervised classification/regression baselines, papers, notes, and legacy notebooks. |
| `neural-cbr/` | `neural-cbr` | Core + full-cycle neural CBR (T1): `model/t1/`, `configs/t1/`, `tools/t1_*`, `tests/test_t1_*`. |
| `rl/` | `rl` | Core + reinforcement learning (T2), including NN-kNN-RL: RL workflows, `model/t2/`, `datasets/rl_tasks.py`, `tools/run_rl_*`, `tools/t2_*`, `tests/test_t2_*`. |
| `llm/` | `LLM` | Core + LLM/agent retrieval (T3): `model/t3/`, `tools/t3_*`, `tests/test_t3_*`. |

The T1, T2 and T3 specifications are Xiaomeng Ye's implementation handoffs in `career-2027/03-research-architecture/implementation-handoff/`.

## What the core is

The authoritative list is `CORE_FILES` in `tools/check_nnknn_core.py`; `tools/nnknn_core_manifest.json` records their SHA-256 hashes. In summary:

- `model/nnknn_model.py`: retrieval model, glocal feature weighting, stable case IDs, case activation, case-store operations.
- `model/nn_cdh.py`: NN-CDH regression and classification adaptation networks.
- `model/feature_extractors.py`, `model/device_utils.py`: representations and CPU/CUDA/XPU handling.
- `model/common/`: model construction and training (`core`), learned distances (`geometry`), prediction and loss (`outcomes`), nominal schema and grouped differences (`nominal`), fingerprints and manifests (`artifacts`), run tracking on TensorBoard event files (`tracking`, below).
- `model/classification_workflow.py`, `model/regression_workflow.py`, `model/mlkr.py` and their loaders in `datasets/`: the supervised baseline layer.
- `datasets/paths.py`: `datasets_root()`, the one place that locates the data. The `datasets/` package holds only loader code; the project data files and preprocessed caches live outside git in one directory shared by all worktrees, `NN-KNN/datasets/` next to the worktrees, or the directory named by `NNKNN_DATASETS`. Library downloads are not kept there: a dataset that a library fetches with a default cache of its own stays in that library's default location (scikit-learn: `~/scikit_learn_data`, or `$SCIKIT_LEARN_DATA`; OpenML: the `openml` cache). Only project data and project-preprocessed caches live in `NN-KNN/datasets/`; torchvision has no default location, so MNIST/CIFAR-10/SVHN stay there too.
- `tools/run_classification_benchmarks.py`, `tools/run_table1_kfold.py`, `tools/resume_table1_kfold.py`, `tools/table1_nnknn_kfold.py`: supervised benchmark runners.
- `tools/check_nnknn_core.py`, `tests/test_nnknn_core.py`, `tests/test_tracking.py`, `tests/test_core_runs.py`, and this file.

Core files never import stage code (`model.t1`, `model.t2`, `model.t3`, RL workflows, `datasets.rl_tasks`). Stage code imports the core, never the reverse. `tests/test_nnknn_core.py` enforces this, including imports inside functions.

## Changing the core

1. Make the change on `main` in `nnknn/`, in a commit that touches only core files.
2. Run `python tools/check_nnknn_core.py --write`, then `python -m pytest tests/test_nnknn_core.py -q` and `python codex/smoke_test.py --mode train --study <name>` (with `NNKNN_RUNS` pointing at a scratch run root).
3. In each stage checkout, copy the core files and the manifest from `main` in one dedicated commit (`git checkout main -- <core files> tools/nnknn_core_manifest.json`), run that branch's tests, and name the source commit in the message.
4. Check all branches from any checkout: `python tools/check_nnknn_core.py --branches main neural-cbr rl LLM`.

Never merge a whole stage branch into another to share core code. A core fix found on a stage branch is first made on `main`, then propagated.

## Run tracking

`model/common/tracking.py` records the training of a run in TensorBoard event files (curves, final metrics, predictions, weights; summaries are files under `results/`, see the rules below); code reads recorded runs back from them. The run root is `NN-KNN/runs/` next to the worktrees, or `$NNKNN_RUNS`; it must exist (it is never created). `runs/<workstream>/<study>/<unit...>/` is one run (workstream `core`, `t1`, `t2` or `t3`). Every process session that writes to a unit adds one event file to that directory; weights stay in it: `weights/<name>.pt` (named states, written once), `weights/resume/last.pt` (the resume checkpoint; the one before it stays as `prev.pt`, so a crash between writing `last.pt` and recording it resumes from `prev.pt`), `weights/<name>.superseded-s<NNN>.pt` (a named state that a later session cut; renamed, never deleted).

```python
data = load_unit(key, config=cfg)               # complete with this config -> RunData, skip (another config raises)
if data is None:
    with open_run(key, config=cfg) as run:      # fresh, resume or restart in place, same directory
        ...                                     # setup; data logged here is discarded in a resumed session
        payload, start = run.load_resume(), 0   # payload is None unless resuming
        if payload is not None:                 # rebuild objects and load payload.state first
            start = payload.step + 1
            payload.restore_rng()               # last, right before the loop continues
        for step in range(start, n):
            ...; run.log_step(step, {"train/loss": loss.item()})   # numbers only: .item() at a sync point
            if run.checkpoint_due(step):        # every 300 s; NNKNN_RESUME_EVERY_SECONDS / _STEPS
                run.save_resume({"model": model.state_dict(), "opt": opt.state_dict()}, step=step)
        run.save_state("best", best_state)
        run.save_rng()                          # only if later code depends on the RNG state the training leaves
        run.log_final({"acc": acc})
    data = load_run(run.path)
model.load_state_dict(data.load_state("best"))  # downstream code loads the recorded weights, never retrains
data.restore_rng()                              # the RNG state the training left (if save_rng was called)
# RunData: final(), series(), record(), records(), array(), table(), states(), load_state(), restore_rng()
```

- Names: unit components are `[A-Za-z0-9_][A-Za-z0-9._=+-]{0,63}`, without a trailing `.`, Windows device names (`aux`, `nul`, `com1`, ...) or embargoed words; units cannot nest. Steps must increase per tag (`log_step` raises otherwise); a float step raises.
- Exact channel: `x/<tag>` (float64/int64/bool), `rec/<name>` (canonical JSON; `log_records` appends rows), `arr/<name>` (`log_array`, `log_table`), `rec/state/<name>` (written by `save_state`), `rec/config`, and the session records `_run/begin|resume|checkpoint|complete|failed`. The display channel (float32 scalars without the `x/` prefix, a session card) is for TensorBoard only. A `torch.Tensor` value raises, so logging never adds a device sync or consumes RNG.
- Resume: `open_run` raises `UnitCompleteError` on a complete unit, `UnitBusyError` if the latest unfinished session's process still runs on this host (pid plus process start identity, so a reused pid or a reboot does not block; a cheap guard, not a lock; `NNKNN_IGNORE_BUSY=1` skips it), or if another launch wrote its session header at the same moment (a launch that sees a rival steps back and its segment is marked withdrawn, so at most one continues), `ConfigMismatchError` if the config changed (unless `resume="restart"`; configs are compared by identity, see below). It resumes when `last.pt` matches the last `_run/checkpoint` record, otherwise it restarts in place (`resume="restart"` or `NNKNN_RESUME=restart` forces that). A resume cuts every data record written after that checkpoint; a restart cuts all earlier data records. Log everything for step S before `save_resume(step=S)`, and use the checkpoint step axis for every tag of a resumable unit. Saved states hold tensors and plain JSON scalars (numpy scalars are converted; other types raise). `load_resume(map_location=...)` moves the state; `restore_rng()` always restores the RNG states on the CPU side.
- `_run/complete` holds `result_digest`, a SHA-256 over the logical stream without `x/sys/*` and without weight-file bytes (`state_sha256` is included). On CPU an interrupted and resumed run has the same digest and state digests as an uninterrupted one (`tests/test_tracking.py` kills a real process to check this). XPU runs record the same digests, but are not promised to match.
- Complete units (owner's rule O4): `load_unit(key, config=...)` returns the `RunData` of a complete unit (or None; `ConfigMismatchError` if it is complete with another config). Call it before any training, never after. `RunData.load_state(name)` loads a named state with its SHA-256 checked (same as `load_state(path, name)`). `Run.save_rng(name="rng", generators=None)` saves `capture_rng()` as a named state (meta `{"kind": "rng"}`); `RunData.restore_rng(name="rng", generators=None)` restores it, so code that runs after a skipped unit starts from the same RNG state as in an uninterrupted run. A snapshot taken with CUDA/XPU initialised restores only where that device exists.
- Identity (owner's order 2026-11-23: units are compared by configuration, not by code): a unit's identity is `config_identity(config)`, the SHA-256 of its canonical config without the top-level provenance keys `tracking.PROVENANCE_KEYS` (`source_sha256`, `source_fingerprint`, `source_fingerprint_sha256`, `source_snapshot`, `code_repository`, `git_commit`, `git`, `dirty`). `resolve_unit`, `load_unit` and `open_run` compare identities, so a unit written by another code state (another source fingerprint, checkout or commit) is the same unit: complete, it is never trained again; incomplete, it resumes. Any other config difference, nested keys included, raises `ConfigMismatchError`. Each session header records `config_identity` next to `config_sha256` (the hash of the full config) and the session's `git_commit`, `dirty` and `source_fingerprint` as information; units written before 2026-11-23 have no `config_identity` field and are compared through their recorded `rec/config`, so they keep matching. `rec/config` holds the config as written (provenance keys included).
- Resume files are kept (owner's rule O5): `weights/resume/last.pt` and `prev.pt` stay in the unit after it completes; nothing deletes them. The device is not part of a unit's identity (not in its key or config).
- TensorBoard after a resume: the Python loader (`tensorboard --load_fast=false`) shows one continuous curve for re-logged tags and hides the stale tail of tags that are not logged again; the Rust loader ignores the SessionLog and keeps those stale points.
- Status (`run_status`): `complete`, `failed`, `incomplete` (crash; a cut or zero-filled last record reads as incomplete), `invalid` (damaged record, digest mismatch, missing or wrong-size weight file, ...) or `empty`. Readers use complete units only. `run_status` and `load_run` check weight files by size; only `verify_run`, `load_state` and `load_resume` check their SHA-256, so read weights through `load_state`, not through `state_path`. CLI: `python -m model.common.tracking {ls|show|verify} <path>`; the reader side needs only `tensorboard` and `numpy`, so on accel: `uvx --with tensorboard==2.21.0 --with numpy python -m model.common.tracking ls ../runs`.

## Owner's rules (2026-11-22)

- R1. Table 1 (`tools/table1_nnknn_kfold.py`, `tools/run_table1_kfold.py`, `tools/resume_table1_kfold.py`: the upstream authors' published regression benchmark) is published work: its code path, its outputs and its numbers do not change. It has no run tracking. Its CLIs, its output files (`summary_long.csv`, `runs_long.csv`, `table1_like.csv`, `transposed.csv`, `done.json`, `resume_manifest.json` in the output folder, and the NN-kNN checkpoint files `checkpoints/nnknn_regression_best_<dataset>_<family>_fold_<k>.pth` with their `_retr` / `_cdh` companions, relative to the working directory), its resume by checkpoint and its seeding (one continuous unseeded sweep over datasets, folds and families) are those of the upstream code. The shared code keeps everything this path calls: `train_model` without a run (checkpoint files), `regression_workflow.train_nnknn_regression_state` without a run (with `checkpoint_label` and `_checkpoint_path_for_run`), and `run_repeated_regression_model_benchmarks` for the baseline methods without `unit_run`. R1 is the only exception to O1-O4.
- R2. Only training data goes to TensorBoard: per-epoch curves, per-run final metrics, predictions and weights. Summaries are not stored as run units.
- O1. Recording is mandatory. Every entry point that trains or evaluates a run requires a study (`--study`, an argparse error without it) and writes its per-run data and weights under `runs/` only; library functions require a run (`run=` an open `tracking.Run`, or `unit_run=`) and raise `TypeError` / `ValueError` without one. There is no file-only mode: no per-run csv/json/checkpoint files outside the unit (Table 1 excepted, R1). Notebooks are not converted; the calls in `notebooks/*.ipynb` that train without a run now raise.
- O2. Summary, report and plotting scripts read only from `runs/` (no reader of old result folders) and write their outputs under `<worktree>/results/` (the default output location; file names, formats and columns unchanged). `results/` is git-ignored. Old result files under `results/` on the experiment host are not touched, moved or converted.
- O3. Reports written by agents or people live in `<worktree>/reports/` and are tracked in git. Generated files (figures, tables, manifests) do not go to `reports/` or `docs/`; scripts that wrote there now default to `results/`.
- O4. Never retrain. A complete unit is never trained again: a rerun detects it before any training (`load_unit`) and loads what it needs from it. Downstream code that needs a trained model (evaluation, later conditions sharing a trained core, pilots, summaries that re-evaluate) loads the recorded weights (`RunData.load_state`) instead of training. Where later computations depend on global RNG state left by the skipped training, the unit records that state (`Run.save_rng`) and the rerun restores it (`RunData.restore_rng`), so a partly rerun study computes the same numbers as an uninterrupted one (tests prove it per workstream).
- O5. Resume files (`weights/resume/*`) are not deleted when a unit completes. The device is not part of unit identity.
- Same seed and device give the same numbers and weights as before these rules (checked against dc2bcd4d on g234 CPU for Table 1 and the classification summaries). One earlier exception, a bug fix (see "Evaluation feature cache" below): NN-kNN with a trainable feature extractor (image `nnknn_conv_trainable`, post-MLP) can report a different test accuracy than dc2bcd4d, because dc2bcd4d evaluated the restored best state with stale case features; keeping the fix awaits the owner's sign-off. `model.common.tracking` loads tensorboard only on first use, so importing the training code or Table 1 (which uses only `NullRun`) needs no tensorboard.

## Recording core training and the benchmark tools

- `core.train_retrieval(..., run=NullRun(), resumable=False, log_prefix="")` logs `train/loss`, `val/loss`, `val/metric`, `case/n_active` (and `val/loss_after_checkpoint`) at step = epoch, each tag prefixed by `log_prefix` as given (a caller that trains twice in one unit passes distinct prefixes ending in `/`, e.g. `"ft/"`). It writes no file itself; stage code calls it with the run of its unit (O1). With `resumable=True` it calls `run.load_resume()` before the loop and, when `run.checkpoint_due(epoch)`, saves a resume checkpoint at the end of an epoch after which training continues (model, optimizer, best state and optimizer, patience counter, history, `case_default_bias`, the permutation generator and the global RNG). `load_resume` can be called once per session, so at most one `train_retrieval` call per unit is resumable. It cannot be combined with a `checkpoint_hook`.
- `nnknn_model.train_model(..., run=NullRun(), resumable=False)`. Without a run (only Table 1 calls it so, R1) it writes its checkpoint files as it always did: the best stage-1 state to `<stem>_retr.pth`, the best stage-2 state to `<stem>_cdh.pth` and the final state to `cfg["checkpoint_path"]` (`nnknn_tmp.pth` in the working directory when unset), reloading the best states from those files. With a run it writes no file outside the run: best states stay in memory, as exact copies on the CPU (no accelerator memory); it logs `val/loss`, `val/acc` (classification) or `val/r2`, and `train/stage` at the global epoch (stage-1 epochs, then stage-2 epochs continuing the count) and saves the named states `best_retrieval` (end of stage 1), `best_adapter` (end of stage 2, when an adapter trains) and `final`. With `resumable=True` it resumes at epoch boundaries of either stage (the checkpoint keeps the `requires_grad` map, so the extractor freeze schedule continues, and `case_default_bias`, which the model draws from the RNG unless `bias_manual_set`) and checkpoints once between the stages, after stage-2 setup. Checkpoints are taken only at epochs after which the same stage continues.
- With or without a run both functions compute the same numbers (same RNG consumption) bit for bit on CPU, and an interrupted and resumed training equals the uninterrupted one (`result_digest`, state digests, history). `tests/test_core_runs.py` checks both; XPU resume is not tested.
- Evaluation feature cache: in eval mode the model caches the case features of its feature extractor, keyed on the case buffer and every extractor parameter and buffer, each by identity, storage address and version counter (identity, so that a new tensor reusing a freed address is not taken for the old one). A restored best state, any `load_state_dict`, an optimizer step or another in-place write refreshes it (a write through `.data` does not: call `_invalidate_case_cache()` after one), so the returned model predicts exactly like a model rebuilt from its final state. Up to 12d4caf (included) `train_model` restored the best state without clearing the cache: with a trainable extractor (post-MLP, `nnknn_conv_trainable`) and a best stage-1 epoch before the last epoch, the returned model evaluated the cases with the extractor of the last validation epoch, so test numbers recorded before this fix differ in those cases. Validation, early stopping and best-epoch selection were not affected (each epoch's training batches cleared the cache). Table 1 (no feature extractor) gives the same numbers with and without the fix.
- Workflows (O1): `train_nnknn_classification_state(state, cfg, *, run, ...)`, `run_single_nnknn_classification_experiment(..., run)`, `run_nnknn_regression_workflow(..., run)` and `run_single_nnknn_regression_experiment(..., run)` require `run`, an open `tracking.Run` (`TypeError` for a missing run or a `NullRun`), and pass it with `resumable` to `train_model`; they write no checkpoint file and no longer take `checkpoint_label`. `train_nnknn_regression_state` keeps its `NullRun` default and `checkpoint_label` for Table 1 only (R1). The caller skips a complete unit before calling them (`load_unit`).
- Benchmark loops: `run_classification_benchmark_methods_on_state` and `run_repeated_classification_model_benchmarks` require `unit_run`; `run_regression_benchmark_methods_on_state`, `run_repeated_regression_model_benchmarks` and `run_repeated_nnknn_regression_experiments` require it whenever `nnknn` is requested (`ValueError`), and run the baselines without it only for Table 1. `checkpoint_label_prefix` is gone. `unit_run(state, method)` is a context manager per method that yields either the open run of that method's unit, which records the method's finals (`accuracy` and `best_metric`, or `rmse_raw`, `rmse_model_space`, `rmse_z`, `best_metric` and the row record `row`), its predictions and the NN-kNN training (resumable), or the `RunData` of the method's complete unit, detected before any training. A complete unit is not rerun: its result entry holds the recorded values (`recorded_unit` = its path, no model). Every method starts from `seed_everything(run_seed)`, so a skipped unit leaves no RNG state that a later one needs. In the image benchmarks the unit whose method trains the shared convnet classifier also saves it as the named state `classifier`; when that unit is complete the loop loads it from there; a complete owner unit without it raises `TrackingError` (never retrained).
- `tools/run_classification_benchmarks.py` requires `--study S` and records one unit per dataset, method and split, `runs/core/S/<dataset>/<method>/<mode>-<index>`; it writes no checkpoint file. Rerunning a study skips complete units, raises `ConfigMismatchError` if a complete unit was written with another config, and resumes incomplete NN-kNN units from their last checkpoint. A holdout or official unit's config holds its `run_seed` but not the run count, so a study can be extended with more `--runs`; a k-fold unit's config also holds the fold count and base seed. It then builds `runs.csv` from the units of this call (dataset, mode, method, run index and seed from each unit's config, `accuracy` from its finals) and `summary.csv` from that, and writes them with `manifest.json` (which carries `"study"`) to a fresh `<--output-dir>/classification_<suite>_<timestamp>/`, default `<worktree>/results/`. File names, columns and contents are those of dc2bcd4d.
- `codex/smoke_test.py --mode train|classification` requires `--study S` and records `runs/core/S/smoke/<mode>`; a complete smoke unit is reported from its recorded finals, not retrained.
- Read results with `load_run` (`series`, `records`, ...), not by scanning raw `x/` tags in the event files: a crashed session may have logged steps after its last checkpoint, which stay in its event file and are cut only by the reader.

## Results and logs

Three places, each with one purpose (O1-O3):

- `NN-KNN/runs/` (next to the worktrees, or `$NNKNN_RUNS`; not in git, backed up regularly): every run's training data and weights, as run units. It is the single source for every summary.
- `<worktree>/results/` (git-ignored): generated summary outputs (csv/json/md/png/pdf), written by summary, report and plotting scripts that read `runs/` only. Table 1 writes its own output folder and checkpoint files as it always did (R1).
- `<worktree>/reports/` (in git): reports and handoffs written by agents or people. No generated file goes there or to `docs/`.

Logs (`logs/`) are not in git either. The stage runners keep no result folders of their own: their per-run data goes to `runs/<t1|t2|t3>/...` and their summaries to `results/`.

Old result files on the experiment host stay where they were written and are not touched, moved or converted; no code reads them any more:

- `main`: `results/prior_baseline/` (pre-MCB NN-kNN results; T1 Phase 0/6 references).
- `neural-cbr`: `results/t1/` and `logs/t1/` by T1 implementation phase.
- `rl`: `results/t2/` and `logs/t2/` by T2 implementation step and benchmark stage.
- `llm`: `results/t3/` and `logs/t3/` by T3 development stage.

The `results/README.md` kept with each branch's old results maps handoff steps to directories, documents, and status.
